## 五、综合评估

### 5.1 做得好的
- 需求**有据可依**:从 PM 实录 + 用户补充提炼,非凭空。
- 终态**关联完整**:需求 ↔ 任务 ↔ 功能模块三表 50/50 双向挂接,字段零缺口,进度自洽(需求/模块进度由任务派生)。
- 代码**可验证**:后端 `dotnet build` 0 error,非纸面方案。

### 5.2 不足(根因分析)
1. **没有先勘清数据模型就动手**。PM 是多表互联模型(需求/任务/功能模块/思维导图/文档 + 外键),我**增量式、被反馈驱动**地逐表补,而不是开工前先把"一个完整项目计划需要填哪些表、哪些外键、哪些必填"摸清。→ 直接导致第 1、2 轮漏表。
2. **把"录入 PM"误解为"写文档"**。第一反应是产出文档而非填充项目管理实体,偏离了 PM 作为项目管理系统的用法。
3. **缺少完整性自检**。每轮只做了"我想到的那张表",没有"这个项目在 PM 里是否字段齐全、关联齐全"的收尾校验 → 第 3 轮的空 `Content` 本应自检发现。
4. **双源风险**:功能地图(mind_map JSON)与功能模块(feature_module 表)我各写一份,内容重复、易漂移。

### 5.3 结论
终态质量达标,但**过程效率低**:本可一轮完成的录入用了四轮、三次返工,根因是"未先建立数据模型全貌 + 缺完整性校验"。教训:**把"录入 PM"当作"填满一个互联模型",开工前先勘模型、收尾必做完整性自检。**

## 六、PM 系统改进建议

> 以下建议直接对应第四、五节暴露的问题 —— 让"这次靠人工提醒才补齐"的坑,被系统机制兜住。

### 6.1 一站式"项目蓝图导入"(最高优先)
提供一个结构化导入接口/能力:接受 `{需求[], 功能模块树, 任务[](带 reqRef/moduleRef)}` 一次建好,并**自动建立 requirement↔task↔feature_module 外键**。
- 解决:逐表手工录入必然漏表(本次漏了 feature_module、漏了 task)。

### 6.2 项目"完整度"校验与缺口提示(类似 lint)
项目详情页给出完整度指标,显式列出缺口:
- 有需求无任务 / 有任务未挂模块 / 任务无描述 / 需求无负责人 / 模块无关联任务 …
- 解决:这次三轮缺口(无任务、无模块、无描述)本可被一个"缺口面板"一次性暴露。

### 6.3 关联进度自动派生(内建,而非靠人手算)
- 需求状态/工时 **= 其任务汇总**(本次我手工 SQL 做了,应内建)。
- 功能模块进度 **= 挂载任务派生**(feature_module 当前**无 Status/进度字段**,建议加派生进度)。

### 6.4 功能地图从数据派生,消除双源
功能地图(mind_map)目前是独立 JSON,与 feature_module/task **不联动**,需各写一份(本次即如此,存在重复与漂移)。建议:**功能地图由 feature_module + task 自动生成**,节点可点击跳需求/任务,单一数据源。

### 6.5 字段约束与默认值
- 任务 `Content`/`Assignee`/`Status`、需求 `Assignee` 等创建时给默认或必填校验(本次 `Content` 允许全空且无提示 → 静默缺口)。

### 6.6 批量操作审计
批量录入/变更自动写 `task_item_log`(表已存在但本次未用),记录谁/何时/改了什么,便于回溯与评估。

### 6.7 AI/Agent 录入契约(项目已有 `IsAiFriendly` 字段,说明有此意图)
对外暴露"项目结构 schema + 写入校验"接口,让 AI 一次拿到全貌(有哪些表、外键、必填、派生关系),**减少逐表试探式录入** —— 这正是本次低效的根源。
