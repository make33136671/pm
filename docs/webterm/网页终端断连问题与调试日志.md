## 三、PM 的具体问题（两个）

### 问题 A：关闭码语义冲突 ——「被顶替」被当成「正常结束」

**位置**：`api/Sb.Apps.Pm.Services/WebTerminals/PtyManager.cs` → `Attach()`

PM 有「单 WebSocket 约束」：同一会话只允许一个客户端，新连接进来会顶掉旧连接。
旧实现顶替时**用了默认关闭码 1000**：

```csharp
// 修复前
_ = prev.CloseAsync("被同账号新连接顶替");   // 实际发出 1000 (NormalClosure)
```

而前端 `Terminal.vue` 把 1000 理解为「会话真的结束了」：

```typescript
const normal = code === 1000 || code === 1001;
if (normal) { emit('closed', '连接已关闭'); return; }   // ← 直接放弃重连
```

**后果**：一旦发生顶替，终端静默失效且**永不自动重连**。
用户感知就是「又断了，还得自己点恢复」。

> 之前那次提交 `cc72dea`「网页终端断连后自动重连」其实写了重连逻辑，
> 但被这条 1000 路径完全绕过 —— **代码写了，但永远走不到**。
> 这也是「明明修过却还是断」的原因。

**哪些操作会触发顶替：**

- 同一个终端会话开了第二个标签页 / 换了设备
- 网络抖动后前端自动重连，而服务端旧连接还未完全清理
- 刷新页面（旧连接尚未 Detach，新连接已 Attach）

### 问题 B：重连竞态 —— 迟到的 close 事件触发重复重连

**位置**：`Terminal.vue` → `destroy()` / `setup()`

`ws.close()` 是异步的。重连时若不加保护：

```
旧连接 close() 发出（异步）
  └─ 新连接建立
       └─ 旧连接的 close 事件此时才到达 → 又调用 scheduleReconnect()
            └─ 重连抖动 / 风暴
```

### 已完成的修复

| 文件 | 改动 |
|---|---|
| `IPtyClient.cs` | 新增 `CloseCodes.Normal = 1000`、`CloseCodes.Replaced = 4001` |
| `PtyManager.cs` | 顶替场景改发 `CloseCodes.Replaced`（4001） |
| `WebTerminalEndpoint.cs` | `CloseAsync` 支持传入 `closeCode` |
| `Terminal.vue` | 识别 4001 → 明确提示「已在其他设备打开」，**不**自动抢回（避免两端互顶）；新增 `wsGeneration` 连接代次，忽略迟到的旧事件 |

**验证状态**：

| 项 | 结果 |
|---|---|
| `dotnet build` Services / WebApi | ✅ 0 错误 |
| `vue-tsc --noEmit` | ✅ 无类型错误 |
| `vite build` | ✅ 构建成功，新逻辑已进 `Terminal-*.js` |
| **部署到 199** | ❌ **未做**（本机为 110，无 ssh/docker 到 199） |
| 提交 git | ❌ 未提交（环境无 `git`） |

## 四、为什么断连「查不清」—— 调试日志现状

这是本文档的重点。当前 webterm 的可观测性**几乎为零**，导致断连只能靠猜。

### 4.1 前端：`dlog` 默认根本不工作

**位置**：`Terminal.vue`

```typescript
const debug = ref(
  /[?&]debug=1\b/.test(...) || localStorage.getItem('webterm:debug') === '1'
);

function dlog(msg: string) {
  if (!debug.value) return;      // ← 未开 debug 时，一切日志直接丢弃
  ...
}
```

| 现状 | 影响 |
|---|---|
| `dlog` 仅在 URL 带 `?debug=1` 或 `localStorage['webterm:debug']='1'` 时生效 | 正常使用**不产生任何断连记录** |
| 已有日志点：`ws-open`、`断连 code`、`重连第 N 次`、`重连放弃`、`ws-error` | 内容其实够用，**只是默认关闭** |
| 日志只推后被端 `clientlog`（需连接还活着） | **连接断开那一刻的日志一定发不出去** ← 致命 |

> 最后一条最关键：断连发生时 `ws` 已经不可用，`dlog` 里的
> `if (ws?.readyState === WebSocket.OPEN) ws.send(...)` 必然失败，
> **最需要的那条日志永远到不了后端。**

### 4.2 后端：连接生命周期完全没有日志

**位置**：`WebTerminalEndpoint.cs`

| 事件 | 当前是否有日志 | 级别 |
|---|---|---|
| 连接建立 / 鉴权成功 | ❌ 无 | — |
| 收到 Close 帧 | ❌ 无 | — |
| `WebSocketException` 断开 | ❌ 无（只 `break`） | — |
| `OperationCanceledException` 断开 | ❌ 无（只 `break`） | — |
| `Attach` 顶掉旧连接 | ❌ 无 | — |
| `Detach` | ❌ 无 | — |
| 控制消息解析失败 | ✅ 有 | **Debug** |
| 客户端 `clientlog` | ✅ 有 | Information |

而生产环境 `appsettings.json`：

```json
"Logging": { "LogLevel": { "Default": "Information" } }
```

**后果**：唯一的异常日志是 Debug 级，**生产根本不输出**。
所以服务端既不知道断没断，也不知道谁断的、什么码断的。

### 4.3 结论

> 现在这套代码里，**「网页终端为什么断」这个问题在线上是不可观测的**。
> 不是日志写得不好，是**该记的地方一条都没记**，记了的又被 debug 开关/日志级别关掉了。

## 五、需要补的调试日志（方案）

按「先能看见，再谈优化」的顺序。等级建议：**Information** 起步，避免被日志级别吞掉。

### 5.1 后端：连接生命周期日志（优先级 P0）

在 `WebTerminalEndpoint.HandleAsync` 补：

| 位置 | 建议日志 | 级别 |
|---|---|---|
| 鉴权通过后 | `webterm 连接建立 s={id} u={user} remote={ip}` | Information |
| 收到 Close 帧 | `webterm 收到客户端 Close s={id} code={code} desc={desc}` | Information |
| `catch (WebSocketException)` | `webterm 异常断开 s={id} err={ex.Message}` | **Warning** |
| `catch (OperationCanceledException)` | `webterm 请求被取消 s={id}` | Information |
| `finally` / Detach | `webterm 连接结束 s={id} 存活={秒}s` | Information |

**关键**：一定要记录**存活时长**和**断开原因分类**。这三个数一出来，
「120 秒规律断开」和「随机断开」立刻能区分开。

### 5.2 后端：顶替与关停日志（P0）

`PtyManager.Attach`：

```csharp
if (prev != null)
{
    _logger.LogInformation("webterm 顶替旧连接 s={SessionId}", sessionId);   // 新增
    _ = prev.CloseAsync("被同账号新连接顶替", CloseCodes.Replaced);
}
```

`PtyManager.Kill` / 会话退出 `CloseAsync`：同样记录原因。

### 5.3 前端：断连日志必须能落盘（P0，最关键）

当前最大的缺陷：**断连那一刻的日志发不出去**。两条路：

**方案 A（推荐，简单）**：断连时先写 `localStorage`，下次连接成功时补发。

```typescript
function dlog(msg: string) {
  const line = `${new Date().toISOString()} ${msg}`;
  // 1. 无论 debug 是否开启，断连类事件先落到本地（保留最近 50 条）
  if (/断连|ws-error|重连/.test(msg)) {
    const buf = JSON.parse(localStorage.getItem('webterm:logbuf') || '[]');
    buf.push(line);
    localStorage.setItem('webterm:logbuf', JSON.stringify(buf.slice(-50)));
  }
  // 2. 连接若还活着，照旧推后端
  if (debug.value && ws?.readyState === WebSocket.OPEN) {
    try { ws.send(JSON.stringify({ type: 'clientlog', msg: line })); } catch {}
  }
}
```

下次 WS `open` 后，把 `webterm:logbuf` 里的积压日志一次性 `clientlog` 上来，
并在成功后清空 buffer。这样**每个用户的重连历史都会自动汇总到后端日志**。

**方案 B（更彻底）**：单独起一个 `sendBeacon` 或独立 HTTP 上报端点，
断连时直接 POST 到后端 `/admin/webterm/clientlog`（不依赖 WS）。

### 5.4 前端：补充断连上下文（P1）

现在 `scheduleReconnect` 只记了 `code`，建议补上：

- `ws.readyState`、连接存活时长（从 `open` 到 `close`）
- `navigator.onLine`（区分断网 vs 服务端关闭）
- 页面可见性 `document.visibilityState`（**移动端切后台常被浏览器杀 WS，这是高频断连来源**）
- 最近一次 ping 的 RTT / 是否有未回复的 pong

> 特别提示「移动端切后台」：很多「莫名其妙断连」其实是浏览器挂起了后台标签页的 WebSocket，
> 并非服务端问题。这条日志能直接排掉一大类误判。

### 5.5 建议的日志分级

| 级别 | 用途 |
|---|---|
| Information | 连接建立/结束、存活时长、顶替 |
| Warning | 异常断开（WebSocketException）、鉴权失败 |
| Debug | 控制消息解析失败等高频噪音（保持现状，生产不输出） |

## 九、Debug 版本实施记录（2026-10-30）

> 本节记录 §5 方案的**实际落地结果**，包含踩到的坑。部署在 110 容器内，`pm.saibo.club`。

### 9.1 后端新增：独立诊断日志文件（关键突破）

**为什么需要**：实测发现线上 Serilog 用 `Async` sink + `restrictedToMaximumLevel` 过滤，
**日志时常不落盘**（异步缓冲未及时 flush）。断连是「一次性事件」，极易丢失。

**方案**：新增 `WriteDiagLog()`，**完全绕开 Serilog**，同步 append + 立即 `Flush(true)`：

```
文件：/opt/pm/api/logs/webterm-diag-YYYYMMDD.log（日期按 UTC）
格式：2026-10-29T18:14:27.110Z [CONNECT] conn=5500921e s=9 user=admin remote=172.17.0.1 ua=
```

日志点（6 处）：

| 标记 | 时机 | 记录内容 |
|---|---|---|
| `[CONNECT]` | 连接建立 | connId、sessionId、用户名、remote IP、UA |
| `[ABNORMAL]` | WebSocketException | 存活秒数、ws 状态、closeStatus、异常消息 |
| `[CANCELED]` | 请求被取消 | 存活秒数（通常是浏览器关闭/刷新） |
| `[CLIENT-CLOSE]` | 收到 Close 帧 | 关闭码、描述 |
| `[END]` | 连接结束汇总 | **存活秒数、断开原因、ping 次数、wsState** |
| `[CLIENT-LOG]` | 前端 HTTP 上报 | 用户名、IP、前端日志正文 |

**实测输出样例**：

```
[CONNECT]     conn=5500921e s=9 user=admin remote=172.17.0.1 ua=
[CANCELED]    conn=5500921e s=9 alive=19s
[END]         conn=5500921e s=9 user=admin alive=19s reason=request-aborted pings=19 state=Aborted
```

### 9.2 后端新增：HTTP 日志上报端点（不依赖 WebSocket）

`POST /webterm/clientlog`

- 接收 `{"sessionId":123,"lines":[...],"ts":...,"ctx":"..."}`
- **鉴权失败也接收**（降级为 anonymous）—— 断连时 token 可能已失效，此时最需要日志
- 返回 `ok diag=<写入路径>`，线上可**直接确认是否落盘**
- 绕过 WS 的根本原因：断连那一刻 ws 已不可用，`ws.send` 必然失败

### 9.3 前端新增：断连日志本地缓冲 + 补发

`Terminal.vue` 的 `dlog()` 重写为三级：

1. **关键事件无条件写 `localStorage['webterm:logbuf']`**（保留最近 80 条）
   —— 不依赖 `?debug=1` 开关，线上默认就收集
2. 连接活着 → WS 推送（带上下文）
3. 连接已断 → `navigator.sendBeacon` POST 到 `/webterm/clientlog`
4. 下次连接成功 → `flushLogBuf()` 补传积压日志

关键事件判定：`/断连|ws-error|重连|关闭|close|error|unload/i`

### 9.4 前端新增：断连上下文采集

每次断连记录：

```
online=<是否联网> vis=<visible|hidden> ua=<UA前60字符> rs=<ws.readyState>
```

以及：

- **存活时长**（`open` → `close` 的秒数）
- **pong 超时**（等待 > 3s 记一条）
- **页面生命周期**：`pagehide` / `visibilitychange` / `offline` / `online`
  —— 移动端切后台杀 WS 是「莫名断连」的高频来源，这条能直接排掉

### 9.5 踩坑记录（重要）

| # | 坑 | 现象 | 解法 |
|---|---|---|---|
| 1 | `ILogger<object>` category | category 是 `System.Object`，被 appsettings 的 `System=Warning` 压掉 Information | 改用 `ILoggerFactory.CreateLogger("Sb.Apps.Pm.WebApi.WebTerminals")` |
| 2 | Serilog Async sink | 日志不落盘 / 延迟极大 | 改用独立文件 + `Flush(true)` |
| 3 | appsettings 重复 key | `Sb.` 和 `SB.` 同时存在 → 启动崩溃 `duplicate key` | 规范化去重 |
| 4 | `dotnet build` ≠ `dotnet publish` | Debug 编译了，Release dll 没更新 | 必须 `-c Release` 且清 `obj/Release` |
| 5 | 进程未真正重启 | `kill` 后 PID 变了但旧进程仍在内存 | 按 `/proc/*/cmdline` 精确匹配后 `kill -9`，并 `sleep` 等端口释放 |

| 7 | 日志文件日期 | 按 UTC 算，与本地日期差一天 | 预期行为，文件名是 `webterm-diag-20261029.log` |

### 9.7 上线后怎么看日志

```bash
# 实时跟踪诊断日志（110 容器内）
docker exec -it dsh-harness tail -f /opt/pm/api/logs/webterm-diag-*.log

# 只看断连
docker exec dsh-harness grep -E 'ABNORMAL|END|CANCELED' /opt/pm/api/logs/webterm-diag-*.log

# 统计断开原因分布
docker exec dsh-harness grep -o 'reason=[^ ]*' /opt/pm/api/logs/webterm-diag-*.log | sort | uniq -c
```

**判读要点**：

- `alive=XXXs` 高度集中在某个值 → 固定超时（如 120s 指向链路层）
- `reason=request-aborted` → 浏览器主动断（关页/刷新/切后台）
- `reason=websocket-exception:*` → 链路异常（配合 `docs/infra/EasyTier-问题报告.md`）
- `[CLIENT-LOG]` 里有 `online=false` → 用户侧断网
- `vis=hidden` 出现在断连前 → 移动端切后台被浏览器挂起
